# RQ3 — Evaluation Design for Vulnerability Explanations

**Authors:** Anonymized for review
**Date:** 16 May 2026

## Research Question

RQ3 — How accurate, useful, and faithful are model-generated vulnerability
explanations when evaluated through a combination of objective metrics and
expert review?

## 1. Scope of Explanation

This work evaluates **local explanations** — explanations attached to
individual model predictions, describing why a specific function was flagged.
We do not evaluate global explanations (explanations of the model's overall
behaviour or learned feature importance across the dataset).

The explanation produced for each prediction consists of three parts:

1. **Evidence tokens** — the top-k tokens from the input that most influenced
   the model's prediction, identified via attention weights from the
   CodeBERT branch of the hybrid model. Default k = 10.

2. **Predicted vulnerability category** — the CWE class (e.g. CWE-121,
   Stack-Based Buffer Overflow) predicted by a secondary classifier trained
   on Juliet's CWE labels.

3. **Natural-language explanation** — a short paragraph generated by a
   hosted large language model, conditioned on the input code, the
   prediction, the predicted CWE, and the evidence tokens. The explanation
   describes the vulnerability mechanism and suggests a remediation.

The explanation is intended to support a developer or analyst in
(a) understanding why a piece of code was flagged, and (b) deciding how
to act on the flag.

### What this work does not claim

- It does not claim to explain the model's behaviour in general (global
  explainability is out of scope).
- It does not claim that the natural-language explanation is a complete or
  verified specification of the vulnerability — only that it is grounded in
  the model's evidence tokens.
- It does not evaluate whether the explanations help non-expert users, only
  whether they are correct, useful, and faithful to the model's reasoning.

  ## 2. Two-Dimensional Evaluation Framework

Explanations are evaluated along two independent dimensions, each measured
by a distinct method:

| Dimension | What it measures | Method | Type |
|---|---|---|---|
| **Faithfulness** | Whether the explanation reflects what the model actually used to make its prediction | Perturbation: mask the tokens identified as important, re-run the model, measure prediction change | Objective, automatic |
| **Human utility** | Whether the explanation supports a human user in understanding and acting on the prediction | Structured rubric scored independently by multiple reviewers | Subjective, human |

The two dimensions are intentionally separated because a fluent explanation
can score high on human ratings while being unfaithful to the model — a
known failure mode of large-language-model explanation systems. Conversely,
a faithful explanation may be technically correct but unreadable to a
developer. A trustworthy explanation must score acceptably on both.

### 2.1 Faithfulness

Faithfulness measures the alignment between the explanation's claimed
evidence and the model's actual decision process. We use a **perturbation-
based faithfulness metric**, which is a standard approach in the
explainable AI literature (variants are used in the ERASER benchmark and
in faithfulness-aware explanation evaluation).

**Procedure** for each explained prediction:

1. Record the model's prediction probability *p_original* for the
   vulnerable class.
2. Take the top-*k* evidence tokens identified by the explanation
   (default *k* = 10, from attention weights).
3. Replace those tokens in the input with the tokeniser's `<mask>` token.
4. Re-run the model on the perturbed input to obtain *p_perturbed*.
5. Record the **faithfulness drop**: Δ = *p_original* − *p_perturbed*.

A large Δ means the model's prediction depended strongly on the tokens the
explanation highlighted — the explanation was faithful. A small or zero Δ
means the highlighted tokens were not what the model actually used — the
explanation was plausible but unfaithful.

Reported metrics: mean Δ across the evaluation set, with standard
deviation. Higher mean Δ indicates more faithful explanations on average.

### 2.2 Human utility

Human utility is measured through structured expert review using a
two-criterion rubric. We deliberately drop "clarity" from the original
proposal because it overlaps with usefulness and adds subjectivity without
adding measurement value.

**Criteria:**

- **Correctness** — Does the explanation accurately describe the
  vulnerability mechanism present in the code?
- **Usefulness** — Would the explanation help a developer with C/C++
  experience locate and remediate the vulnerability?

Each criterion is rated on a 1–5 scale with anchor descriptions provided to
reviewers (see Section 3). Reviewers see the code and the explanation only;
they are blind to the model that produced the explanation.

### 2.3 Why both dimensions matter

A single number, whether faithfulness or human rating alone, can be
misleading:

- High faithfulness, low usefulness → the explanation reflects the model
  but doesn't help the user. The model may be relying on superficial
  features.
- Low faithfulness, high usefulness → the explanation reads well but is
  detached from the model's reasoning. This is the "plausible but wrong"
  failure mode that the previous review flagged for LLM-based explanations.
- High on both → the explanation is grounded in the model's evidence
  *and* communicates that evidence usefully. This is the target.

Reporting both dimensions allows us to identify which failure mode (if
any) the system exhibits, rather than presenting a single aggregate that
hides the trade-off.

## 3. Rubric Specification

Reviewers rate each explanation independently on the two criteria defined
in Section 2. Each criterion uses a 1–5 scale with explicit anchor
descriptions to reduce inter-rater variance.

### 3.1 Correctness rubric

> *Does the explanation accurately describe the vulnerability mechanism
> present in the code?*

| Score | Anchor description |
|---|---|
| **5** | The explanation correctly identifies the vulnerability type and accurately describes the mechanism (e.g. how the unsafe operation can be exploited). All technical claims about the code are correct. |
| **4** | The explanation correctly identifies the vulnerability and describes the mechanism, with at most one minor technical inaccuracy that does not change the substance. |
| **3** | The explanation identifies the correct vulnerability category but the mechanism description is partially wrong, vague, or generic (e.g. "this is unsafe" without specifying why). |
| **2** | The explanation identifies a related but incorrect vulnerability, or correctly identifies the category but the mechanism description contains significant errors. |
| **1** | The explanation misidentifies the vulnerability entirely, or claims a vulnerability where the code is safe, or describes a mechanism not present in the code. |

### 3.2 Usefulness rubric

> *Would the explanation help a developer with C/C++ experience locate and
> remediate the vulnerability?*

| Score | Anchor description |
|---|---|
| **5** | The explanation pinpoints the specific lines/expressions involved, explains why they are unsafe, and suggests a remediation that would resolve the issue. A developer could fix the code from the explanation alone. |
| **4** | The explanation pinpoints the issue and explains it, but the remediation suggestion is generic or requires the developer to fill in details. |
| **3** | The explanation locates the general area of concern but is too abstract to drive a fix without further investigation. |
| **2** | The explanation is vague about location, mechanism, or remediation, and a developer would need to substantially re-analyse the code. |
| **1** | The explanation does not meaningfully help — too generic, misleading, or actively unhelpful. |

### 3.3 Rater protocol

Each reviewer receives:

- The function source code (unannotated)
- The model's prediction (vulnerable / safe) and confidence
- The model's predicted CWE category
- The natural-language explanation

Reviewers do **not** receive:

- The model identity (CodeBERT, GraphCodeBERT, hybrid, or which version)
- The ground-truth label or CWE from the Juliet dataset
- Other reviewers' scores

Each reviewer scores all sampled explanations independently. Reviewers may
add a brief free-text note when a score is at the extremes (1 or 5) or
when the explanation has an unusual property (e.g. correct vulnerability
but wrong code line). Free-text notes are qualitative supporting evidence,
not part of the quantitative analysis.

### 3.4 Sample selection

The evaluation sample is drawn from the test partition of Juliet. Sample
size: **40 explanations**, balanced across the four most common CWE
categories in the dataset (CWE-121, CWE-78, CWE-190, CWE-191), with 10
explanations per category. Within each category, half are sampled from
correctly classified positives (true vulnerable predictions) and half
from false positives (safe code that the model flagged as vulnerable) to
ensure the evaluation covers both success and failure modes.

This sample size is a deliberate compromise. A larger sample would
strengthen statistical claims but is not feasible in the practicum
timeline. The trade-off is acknowledged as a limitation in Section 6.

## 4. Reviewer Recruitment, Reliability, and Conflict Handling

### 4.1 Reviewer profile

Reviewers are recruited from the cohort of MSc Computing students at
the host university with demonstrated familiarity with C and C++.
Specifically, reviewers are required to have:

- Completed at least one module involving C or C++ programming
- Familiarity with common security concepts at the level of an
  introductory secure-programming course (buffer overflows, integer
  overflows, command injection, format-string issues)

Reviewers do not need formal security research experience. The evaluation
asks whether the explanation is **understandable and actionable to a
developer**, not whether it satisfies a security researcher's full
threat model. This is consistent with the deployment context (assisting
developers, not replacing security teams) and is stated explicitly as a
scope choice rather than a limitation.

### 4.2 Number of reviewers

The evaluation uses **three reviewers**, including one of the project
authors. Each reviewer rates all 40 sampled explanations independently.

Three is a deliberate minimum:

- Two reviewers can compute inter-rater reliability but cannot identify
  outliers or majority/minority patterns.
- Three reviewers allow majority resolution of disagreements and reveal
  whether disagreements are systematic or noise.
- More than three would strengthen claims but is not feasible given the
  practicum timeline and the unpaid voluntary nature of recruitment.

The use of a project author as one reviewer introduces a known bias
toward favourable scores. To control for this, the project author's
scores are reported alongside but excluded from the headline averages
used in the analysis. This is stated openly in the limitations.

### 4.3 Inter-rater reliability

Inter-rater reliability is computed using **Cohen's kappa (κ)** for each
pair of reviewers, on each criterion independently (correctness and
usefulness).

| κ range | Interpretation |
|---|---|
| < 0.20 | Poor agreement — results not reliable |
| 0.21 – 0.40 | Fair agreement |
| 0.41 – 0.60 | Moderate agreement (acceptable for this work) |
| 0.61 – 0.80 | Substantial agreement |
| > 0.80 | Near-perfect agreement |

For three reviewers, **Fleiss's kappa** is also reported as a global
agreement measure. A pre-stated minimum acceptable threshold is
κ ≥ 0.40 (moderate agreement) for the evaluation to be considered
informative. If observed κ falls below this threshold, the disagreement
itself is treated as a finding and discussed rather than papered over.

### 4.4 Handling disagreement

When reviewers disagree by more than 2 points on a single explanation
(e.g. scores of 2, 4, 5), the case is flagged for qualitative analysis.
Such disagreements are not resolved by averaging; they are reported as a
distinct subset in the results, and the reviewers' free-text notes are
examined to understand the source of the disagreement (different
interpretations of the rubric, different assumptions about the deployment
context, or genuine ambiguity in the explanation).

This protects against a common failure mode where averaging high-variance
scores produces a deceptively confident-looking number.

### 4.5 Ethics

The evaluation involves only informal peer review of model-generated text
by adult MSc students participating voluntarily. It does not collect
personal data, does not involve sensitive content, and does not place
participants at risk. Reviewers are informed in writing of:

- The purpose of the evaluation
- What they are being asked to rate
- That their participation is voluntary and they may withdraw at any time
- That their individual scores will be reported as anonymised reviewer IDs
  (R1, R2, R3), not by name

A formal application to the DCU School of Computing ethics process will
be submitted in parallel with the project. If a fast-track or exempt
status is available given the low-risk nature of the activity, this will
be sought. The supervisor's guidance on the appropriate ethics route is
explicitly requested.

## 5. Threats to Validity and Limitations

The RQ3 evaluation makes deliberate trade-offs to fit the practicum
timeline. We name them openly here rather than discovering them as
critiques at the viva.

### 5.1 Small reviewer pool

Three reviewers is the minimum for outlier detection and majority
analysis. It is not sufficient to support strong statistical claims about
the broader population of developers. Reported inter-rater reliability
should be interpreted as an indicator of rubric consistency within this
specific cohort, not as evidence of generalisability.

**Mitigation:** all individual reviewer scores are reported alongside
aggregates so readers can inspect the underlying agreement themselves.
Disagreements are analysed qualitatively rather than averaged away.

### 5.2 Author as reviewer

One of the three reviewers is a project author. This introduces a known
bias toward favourable scores, since the author has investment in the
work succeeding.

**Mitigation:** the author's scores are reported separately, and the
headline averages reported in the dissertation results exclude the
author's ratings. The author's ratings are retained only for inter-rater
reliability comparison.

### 5.3 Sample size

Forty explanations across four CWE categories is a working compromise.
With ten explanations per CWE and split across true positives, false
positives, and false negatives, individual cell sizes are small (between
two and six explanations). Per-CWE claims should be read as indicative
rather than statistically rigorous.

**Mitigation:** we explicitly avoid per-CWE significance claims and
instead report patterns. Aggregate claims across the full 40-explanation
sample are reported with appropriate uncertainty.

### 5.4 Synthetic dataset

The evaluation is performed entirely on the Juliet Test Suite, which is
synthetic. Real-world C and C++ code is more variable in style, naming,
and structure. Explanation quality observed on Juliet may not transfer
directly to production code.

**Mitigation:** the dissertation frames Juliet results as upper-bound
performance and notes the synthetic-to-real-world gap as the most
important direction for future work.

### 5.5 LLM-generated explanations

The natural-language explanations are produced by a hosted large language
model conditioned on the input code and the attended tokens. The quality
and consistency of explanations therefore depend partly on a model that
this project does not control or train. The same model and prompt may
produce different explanations on different runs (sampling variance), and
the model may improve or change over the project's lifetime.

**Mitigation:** the explanation pipeline records the model version and
prompt used for each generated explanation. The faithfulness metric
provides a model-independent check on whether the explanation, however
fluent, reflects the underlying classifier's reasoning.

### 5.6 Faithfulness perturbation method

The perturbation procedure masks tokens identified as important and
measures prediction change. This is a standard faithfulness approach but
has known limitations:

- It measures *sufficiency* (the explanation is enough to drive the
  prediction) rather than *comprehensiveness* (the explanation covers
  all important features).
- It assumes the model behaves sensibly on inputs with masked tokens, an
  out-of-distribution condition the model was not trained for.

**Mitigation:** we report faithfulness as an indicator alongside human
ratings rather than as a definitive measure. The two dimensions together
provide a more honest picture than either alone.

### 5.7 No formal ethics approval at submission time

If the DCU ethics fast-track or exempt status is not granted within the
timeline, the evaluation is conducted as informal peer review under the
voluntary-participation protocol described in Section 4.5. This is
acknowledged as a methodological compromise and the implications for
generalisability are stated explicitly.

- Test set predictions, including a labelled mix of true positives, false positives, and false negatives, are available (Week 3 deliverable).

These dependencies are the reason the explanation pipeline implementation
is scheduled for Week 2 — the pipeline can be built and tested on dummy
predictions while waiting for the real model outputs.

### 6.3 Outputs feeding the dissertation

The RQ3 work produces:

- A faithfulness analysis: distribution of Δ values across the 40 sampled explanations, with summary statistics.
- A human-utility analysis: correctness and usefulness ratings per explanation, with per-reviewer breakdowns.
- Inter-rater reliability: pairwise Cohen's kappa and overall Fleiss's kappa, per criterion.
- Disagreement subset: cases where reviewers diverged by more than 2 points, with qualitative analysis of why.
- One worked example per CWE category: a complete walk-through of an explanation, its faithfulness score, and the reviewer ratings, for inclusion in the results chapter.

These outputs feed directly into the dissertation chapters on Methodology
(Sections 2-4 of this design doc) and Results (Section 6.3 outputs).

## Additional Threat: Residual Label Leakage

Deduplication removed exact duplicate code strings but did not remove
Juliet-specific annotation tokens such as FLAW, POTENTIAL, and FIX
embedded in the source code of vulnerable functions. These tokens remain
as residual label leakage and contribute to near-perfect scores across
all models including the Random Forest baseline. This is acknowledged
as a limitation of the Juliet dataset rather than a methodological error,
and is consistent with the three-artefact diagnostic findings reported
in the main results.
